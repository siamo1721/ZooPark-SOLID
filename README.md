# ERP-система для Московского зоопарка

## 1. Описание предметной области

Данная программа моделирует упрощённую ERP-систему для зоопарка.  
Система отражает базовые аспекты функционирования зоопарка:

- хранение информации о животных разных видов;
- работу сотрудников зоопарка;
- процессы ухода за животными (кормление, лечение, уборка);
- формирование отчёта по животным.

Основной целью является не реализация полноценной бизнес-системы, а демонстрация корректного применения принципов SOLID в реалистичном предметном контексте.

---

## 2. Применение принципов SOLID

### 2.1 Single Responsibility Principle (SRP)

Каждый класс в системе имеет одну зону ответственности.

**Примеры:**
- `Animal` и его наследники (`Lion`, `Parrot`, `Snake`) отвечают только за описание животного.
- `Keeper` отвечает только за кормление и уборку.
- `Veterinarian` отвечает только за лечение.
- `ZooReportService` отвечает только за формирование отчёта.


Таким образом, изменение логики отчётов не влияет на животных или сотрудников, и наоборот.
```java
public abstract class Animal {
    protected String name;

    public String getName() {
        return name;
    }
}
```
⸻

### 2.2 Open/Closed Principle (OCP)

Система открыта для расширения, но закрыта для модификации.

Примеры:

	•	Чтобы добавить новое животное, достаточно создать новый класс-наследник Animal.
	•	Чтобы добавить нового сотрудника, создаётся новый класс, реализующий нужные интерфейсы.
```java
public class Elephant extends Animal {
    public Elephant(String name) {
        super(name);
    }
}
```
Существующий код при этом не изменяется.

---

### 2.3 Liskov Substitution Principle (LSP)

Все наследники базовых классов могут использоваться вместо своих родителей без нарушения логики программы.

Примеры:

	•	Lion, Parrot, Snake могут использоваться везде, где ожидается Animal.
	•	Все сотрудники (Keeper, Veterinarian) корректно подставляются вместо Employee.
```java
Animal animal = new Lion("Симба");
```
Программа продолжает работать корректно независимо от конкретного типа животного.

---

### 2.4 Interface Segregation Principle (ISP)

В системе используются небольшие, специализированные интерфейсы вместо одного универсального.
```java
public interface Feedable {
    void feed(Animal animal);
}
```
```java
public interface Cleanable {
    void clean(Animal animal);
}
```
```java
public interface Healable {
    void heal(Animal animal);
}
```
Примеры:

	•	Keeper реализует Feedable и Cleanable.
	•	Veterinarian реализует только Healable.

Таким образом, классы не зависят от методов, которые им не нужны.

---

### 2.5 Dependency Inversion Principle (DIP)

Код зависит от абстракций, а не от конкретных реализаций.

Примеры:

	•	Отчёт формируется через интерфейс ReportGenerator.
	•	Работа с животными осуществляется через базовый тип Animal.
```java
ReportGenerator report = new ZooReportService();
report.generate(animals);
```
Это позволяет легко заменить реализацию отчёта (например, на файловый или веб-отчёт).

## 3. Ограничения и потенциальные проблемы расширения

При усложнении бизнес-логики могут потребоваться дополнительные абстракции:

	•	сложные медицинские процедуры;
	•	хранение истории лечения и кормления;
	•	разные типы отчётов.

В текущей версии система предназначена для демонстрации архитектурных принципов и не покрывает сложные сценарии.

---

## 4. Почему введённые абстракции улучшают дизайн

Использование абстрактных классов и интерфейсов позволило:

	•	снизить связность между компонентами;
	•	упростить добавление нового функционала;
	•	сделать код читаемым и поддерживаемым;
	•	чётко разделить доменную модель и бизнес-логику.

Архитектура остаётся гибкой даже при росте системы.
